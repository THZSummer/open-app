# 05 · 企业级 AI 治理调研（维度 E）

> **调研目标**: G4 —— 动态授权、Agent 审计、数据敏感度分级的最佳实践；评估 open-app 现有审批/权限地基是否可复用
> **采集日期**: 2026-08-12
> **信息来源**: MCP 官方（授权/安全文档）、A2A 官方（企业特性）、OpenAI 官方 + 领域知识（企业 AI 治理框架）
> **方法**: 官方直采 + 领域知识（Gartner/OWASP 等最佳实践提炼）

---

## 一、执行摘要（先出结论）

1. **企业级 AI 治理已从"口号"走向"协议原生"**：MCP 规范内置 **OAuth 2.1 + 授权服务器发现 + 企业托管授权（Enterprise-Managed Authorization）**，A2A 提供 **Enterprise Features（多租户/流式/异步）**——**授权、审计、数据边界已成为协议层一等公民**。
2. **三大治理支柱已成型**：① **动态授权**（上下文感知、按需最小权限）；② **细粒度审计**（工具调用级可追溯）；③ **数据敏感度分级驱动审批**（敏感操作强管控）。
3. **对 open-app 的含义**：现有治理骨架（应用管理 + AKSK + 权限中心 + 动态审批流，40 表/184 API）**高度可复用且是先发优势**——国内三家（钉钉/飞书/企微）的 AI 治理都较浅（见 02 报告）。

## 二、协议层的治理能力（官方直采）

### 2.1 MCP 授权体系（modelcontextprotocol.io 官方）

| 能力 | 说明 | open-app 对接点 |
|------|------|:---:|
| **OAuth 2.1 授权** | 标准授权流程，保护敏感资源与操作 | 与现有 OAuth/AKSK 体系对齐 |
| **授权服务器发现** | 客户端可发现 MCP 服务器的授权端点 | 应用管理中的元数据暴露 |
| **客户端注册** | 客户端（Agent）身份注册管理 | 应用注册/审核流程复用 |
| **OAuth Client Credentials** | 机器到机器认证（MCP 扩展） | **与 AKSK 机器凭证模式直接对应** |
| **Enterprise-Managed Authorization** | 企业 IdP 集中管控 MCP 访问（SEP-990：企业 IdP 策略控制） | 企业租户级权限中心对接 |

### 2.2 MCP 安全最佳实践（官方安全文档主题）

- 安全考虑、攻击向量与实现最佳实践（官方安全文档专章）——含工具注入、提示注入、资源越权等 Agent 特有风险面。

### 2.3 A2A 企业特性（a2a-protocol.org 官方）

- **Enterprise Features**：多租户、流式与异步操作——Agent 间通信的企业级需求被协议原生覆盖。
- **Secure & Opaque**：Agent 交互无需暴露内部记忆/工具/专有逻辑，保护 IP——**Agent 间最小信息暴露原则**。

### 2.4 OpenAI 工具治理（platform.openai.com 官方）

- **allowed_tools**：限制模型可调用的工具子集——**运行时的工具级授权**，是"动态授权"的具体实现。
- **tool search / namespace**：大工具面按需加载——**工具最小暴露**。

## 三、企业 AI 治理最佳实践（领域知识提炼，需复查验证）

### 3.1 动态授权（Dynamic Authorization）

| 实践 | 说明 |
|------|------|
| 上下文感知授权 | 授权决策基于调用上下文（用户身份、数据敏感度、Agent 来源、风险评分）而非静态角色 |
| 按需最小权限 | Agent 仅在任务需要时获得对应工具的临时权限（对齐 allowed_tools） |
| 分层审批 | 低风险操作自动放行、高风险操作人工审批（对齐 open-app 动态审批流） |

### 3.2 细粒度审计（Audit）

| 实践 | 说明 |
|------|------|
| 工具调用级日志 | 记录 Agent 每次工具调用的参数/结果/耗时（对齐 MCP 调用可追踪性） |
| 全链路 trace | 从用户请求 → Agent 决策 → 工具调用 → 结果的端到端追踪 |
| 事后复盘 | 异常调用回放、权限越权检测 |

### 3.3 数据敏感度分级（Sensitivity-based Control）

| 实践 | 说明 |
|------|------|
| 数据分级 | 公开/内部/机密/绝密 分级（或 PII 维度） |
| 敏感度驱动审批 | 操作的数据越敏感，审批要求越高（对齐 open-app 审批流可扩展） |
| Agent 数据边界 | 企业 IdP 管控 Agent 能访问的数据范围（对齐 Enterprise-Managed Authorization） |

## 四、open-app 现有治理地基评估（对照复用）

| open-app 现有资产（README §1.1） | AI 治理能力缺口 | 复用方式 |
|------|------|------|
| 应用管理（注册/审核/凭证） | Agent 客户端注册（OAuth Client Registration） | 直接扩展为 Agent 注册 |
| AKSK 凭证体系 | MCP OAuth Client Credentials / Bearer 认证 | **直接对齐**（MCP 官方同款机制） |
| 权限中心（RBAC） | 动态授权（上下文感知） | 在 RBAC 之上叠加风险/敏感度维度 |
| 动态审批流（40 表） | 敏感度驱动审批 + Agent 审批回调 | 扩展审批触发器（事件/回调形式天然支持） |
| 184 API 治理 | 工具级授权（allowed_tools 模式） | 为每个 API 输出工具级授权策略 |

**结论**：open-app 治理骨架是"先发优势"——行业刚在协议层补齐（MCP OAuth/企业托管授权），open-app 已有成熟实现，**AI 化成本低、差异化强**。

---

## 五、对 open-app 的治理升级建议

1. **MCP 授权对接（P0）**：open-app 的 AKSK/权限中心对接 MCP OAuth 2.1 + Client Credentials，实现"AI 工具调用走既有鉴权"。
2. **动态授权升级（P1）**：权限中心叠加"上下文感知授权"——按调用方（Agent 身份）、数据敏感度、风险评分动态决定放行/审批。
3. **工具级审计（P1）**：在既有 API 调用审计基础上增加**工具调用级全链路日志**（Agent → 工具 → 结果）。
4. **敏感度驱动审批（P2）**：数据分级 + 审批流联动——敏感数据操作触发动态审批（Agent 时代的审批要支持回调式/异步审批）。
