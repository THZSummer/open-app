## 1. 执行摘要

**一句话结论：把「文件/字节」当作不进入 JSON 对象图的对象引用/流句柄（而不是把文件内容内联进 JSON）是业界主流数据形态；把「透传式文件搬运」与「脚本/表达式对字节做加工」明确分档、只对加工开一道带配额的受限通道，也与主流安全边界一致。行业的差异化主要不在"能不能传文件"，而在"文件能传多大、是否流式/落盘、加工时的安全边界与存储治理"。**

### 1.1 核心判断（全部可追到附录证据，未核实项已标注）

| # | 判断 | 支持证据 | 证据级 |
|---|------|---------|:---:|
| 1 | 成熟平台普遍存在「文件/二进制与 JSON 分开存」的第二数据形态，且多以"引用 + 独立存储 + 消费时流式读写"呈现，而非 base64 内联 | Workato FileStorage（句柄化文件服务）、n8n binary data store（json 与 binary 分列）、MuleSoft DataWeave `Binary` 一等类型、Boomi 以 input/output data stream 管理 | ① |
| 2 | 「透传（字节搬运）先于/独立于加工」是普遍产品切法；文件搬运可在不解释字节的情况下完成，只有加工才需要"摸到"字节 | Workato：二进制文件"不解释内容直接搬"；URL 直传 vs file content 两档（后者才支持读/加工且被明确提示大文件慢） | ① |
| 3 | 大文件几乎都不走"请求体全量内存"；策略是**对象存储/托管文件存储中转 + 引用传递**，或**分块/流式 API**，或**落临时盘**；内存上限是普遍硬约束 | AWS Lambda payload 6MB、S3 multipart 5MB–50TB 且大对象走"盘→流"直传；n8n database 模式单文件 512MiB 上限；Workato 大文件建议用 URL 直传而非 file content | ① |
| 4 | 「脚本/代码/表达式加工二进制」与沙箱的张力是行业普遍课题：要么不提供（只透传）、要么给受限通道/内建节点、要么干脆放弃沙箱（自担风险） | n8n 代码节点 `getBinaryDataBuffer()` 需显式 API 取二进制；Workato 加工主要靠内建工具节点（File tools / SQL 转换）而非任意脚本；Node-RED 由 function 节点全权操作 Buffer（无沙箱） | ① |
| 5 | 断点续传/分片/秒传通常是"平台文件能力/对象存储层"的事，而非编排引擎的职责；把它们列为编排引擎 Non-Goal 与行业一致 | AWS S3 把 multipart/presigned 放在存储服务；企微把"分块上传/异步上传"放在微盘/素材 API（上游），编排不重造 | ①（S3/企微） |
| 6 | 托管文件存储的引用通常带**有效期/TTL 与租户/空间隔离**，且**不自动清理**的产品会要求用户显式删除（治理成本高） | Workato FileStorage 无自动删除、需手动删；企微 media_id 仅 3 天有效 | ① |

### 1.2 与我们既定决策的对标（详见 §5）

- **FileRef 句柄式**：行业无例外地支持"以引用/ID/URL 表示文件、内容存在独立存储"，且普遍用"过期时间/空间/引用计数"做治理 → **路线 B 方向被印证**；可作为差异化参考的是各家对"引用粒度"与"文件是否流经编排"的取舍（Workato 的 URL 直传 = 文件完全不流经编排；n8n 的 binary data store = 文件在编排内以句柄流转）。
- **S4 沙箱受限 fs API 白名单**：没有找到任何主流平台"把任意字节放给多租户脚本自由 IO"的先例；可借鉴先例是 n8n 显式 `getBinaryDataBuffer()`（沙箱内 API 才拿得到 Buffer）与 Workato "File tools" 内建受限工具节点。
- **Non-Goal（断点/分片/秒传/转码）**：分片/断点普遍存在于平台的文件存储层或上游对象存储，编排引擎普遍不实现 → 合理性成立；**但需注意**："透传 + 流式"与"HTTP Range"天然兼容（我们列为二期），行业内网关/存储层普遍支持 Range，是低成本加分项，不建议永久性排除。

## 4. 各家分节深读

> 深读原则：**只写有证据级①支撑的机制细节**；与我们的 FileRef/透传/加工模型直接相关的实现单独加「对我们 FileRef 的借鉴点」。

### 4.1 n8n（开源工作流编排）—— binary 数据与 JSON 分域 + 可切换落盘模式

n8n 与我们"FileRef：字节不进 JSON 对象图"的决策**同构**，是最值得对照的实现样本。

**核实到的机制（证据①）：**

1. **数据形态**：n8n 数据项由 `json` 与 `binary` 两部分组成，文件型数据（image/document 等）作为 **binary data** 与 JSON 分离保存，节点间流转的是引用而非把文件塞进 JSON（docs.n8n.io，Work with files and images）。文件的读写由专门节点承担：`Convert to File`（JSON→文件）、`Extract From File`（文件→JSON）、`Read/Write Files from Disk`（读写运行机磁盘）、`Compression`、`Edit Image`、FTP 等——即"**文件操作内建为节点能力**，而不是让用户脚本碰裸字节"。
2. **存储模式可切换（关键设计）**：n8n 默认把 binary data **放内存**，官方明确警示"working with large files 会崩"；自托管可把 `N8N_DEFAULT_BINARY_DATA_MODE` 设为 `filesystem`（落盘，路径默认 `<userFolder>/binaryData`）、`s3`、`azure` 或 `database`（Boomi/env var 页）。**队列（queue）模式必须用 `database`，不支持 `filesystem`**（规模化后 binary 要进共享存储而非本机盘）。
3. **大小与生命周期**：`database` 模式单文件上限默认 **512MiB、最大 1024MiB**（超过即失败）；binary 数据清理随 execution data 修剪策略执行（与"执行记录保留"联动）。
4. **脚本加工的安全面**：代码节点拿二进制**不是直接访问**，而是通过显式 API `this.helpers.getBinaryDataBuffer(itemIndex, propertyName)` 返回 Buffer（Python 不支持）——即"沙箱内开一道受控取字节口"的形态。读/写文件节点有安全提示，必要时用 `NODES_EXCLUDE` 整体禁用。
5. **大文件治理路径**：官方建议走 filesystem/外部对象存储，并提供外部存储文档（Business/Enterprise 自托管）。

**对我们 FileRef 的借鉴点：**
- "json 与 binary 同 item、并列双域" = 我们的"JSON Map 座位 + FileRef 句柄"的现成范本；它们甚至不引入额外封装字段，直接类型化。
- 二进制**不进 DB 快照/日志**，随执行数据统一修剪 → 印证我们"日志只记 FileRef 元数据"。
- **filesystem 模式与 queue 模式的冲突**提醒我们：本地临时盘方案在"多实例/队列化"部署下要换成共享对象存储（我们 MVP 的落盘方案需在架构上给 S3/MinIO 留口）。
- 脚本取字节走"显式 API + 受上限约束"而非自由 IO → 支持我们 `ctx.fs.readBytes(fileRef, {maxBytes})` 的白名单思路。

### 4.2 Workato —— 流式 chunk 搬运 + "URL 直传 vs file content"两档 + FileStorage 句柄化托管存储

Workato 是本次调研中与 S1–S4 划分**对齐度最高**的商用 iPaaS。

**核实到的机制（证据①）：**

1. **文件搬运两档（本质 = 透传 vs 可加工的分界）**（Handling binary files）：
   - **档位 A「public URL 直传」**：拿到源文件公共 URL → 直接交给目标 app 下载，**文件完全不经过 Workato**；官方明确"非常推荐用于超大文件（moving very large files using a public URL），因为 file content 方式大文件会很慢"。
   - **档位 B「file content」**：Workato 先把内容下载进来再上传给目标，**只有这一档能读/加工文件数据**（download → transform → upload）。
   - 这正是我们"透传 vs 加工"的本质差异：加工 = 内容进编排；纯搬运 = 引用/URL 层面完成。Workato 把"文件流经编排与否"做成用户可选，而不是架构上二选一。
2. **File streaming（分块搬运，针对超大文件）**（File streaming）：流式 = 把一个文件切成小片、逐片下载+逐片上传、按序重组；**只要源与目标两端都支持 streaming，可搬运"任意大小"的文件**，且流式动作是长/延迟动作，**不会因耗时超时**。无需配置，把 source 的 `File contents` datapill 传给 dest 的 `File contents` 输入即自动触发。**例外**：HTTP connector 的 Send request 动作需把 **Wait for response + Enable streaming** 都设 Yes 才能把响应当流传给下游（含不支持 streaming 的下游）。
   - 覆盖列表（节选）：S3（Upload file (streaming)、Download file contents）、SFTP、Box、Google Drive、OneDrive（Upload large file via session）、FTP（Download large file action 单列）、HTTP connector 等。
3. **二进制不解释移动**（Handling binary files）：binary 文件"move without interpreting its content"；只有对接只认 base64 的 app 时才用公式做 base64 encode/decode。
4. **FileStorage = 句柄化托管文件存储**（Workato FileStorage）：Create/append/get file contents + 目录 + search，加密（账户级密钥月度轮换 + BYOK）；数据不自动删除、需显式清理；**存储/UI 需向 CS 开通（限企业套餐）**；connector 访问不限角色（工作区内全员可见），UI 才有 RBAC。限额数字官方发布但为 JS 渲染（limits 页 `<LimitTable>`）无法静态提取。
5. **大文件之外还有 batch 路径**：批量触发/批量动作 + SQL 转换 + FileStorage 聚合，覆盖"记录级"大文件（如 100 万行 CSV 落 FileStorage 再 bulk 灌 Salesforce）——与我们 S3 大文本透传是互补视角（他们是"拆记录"而非"透传字节"）。

**对我们 FileRef 的借鉴点：**
- "引用在 datapill 层面透传，字节在两端 streaming" ≈ 我们的 FileRef + 入口落盘/出口旁路写回。它们没有把临时字节显式建模为"文件对象引用"，但效果相同。
- **URL 直传**档提示我们：MVP 之外，"FileRef 的 URL 化/预签名化"可作为扩展（我们评估报告把"二次 URL 跳转下载端点"列为非主方案；Workato 证明"URL 直传"在**上传→转发**语义上价值很大，但在**下载→返回调用方**语义上会改变契约，与我们的取舍一致）。
- **加工才需要内容进编排**的表述，是给产品/售前讲 S1–S4 分档的最好行业话术。

### 4.3 MuleSoft / Boomi（企业重型）—— Binary 一等类型 + 以"流"为管理单元

重型平台的共性是把"文档/负载"当**流**管理，字节在内存/盘间按流进出，加工则落在 DataWeave（Mule）或 map/脚本（Boomi）。本次受文档站抓取限制，只核实到类型与资源管理两层。

**MuleSoft（证据①，仅类型层）：**
- DataWeave 有一等 **`Binary`** 类型（官方定义即 "A blob"），且可并入 String 可强转联合（StringCoercible 含 Binary、Uri 等）——意味着二进制在表达式世界里以"可转字符串的 blob（实践中为 base64 字符串）"参与加工（dw-core-types）。
- DataWeave 存在 **Multipart/Attachment 类型模块**（类型索引列出 dw::module::Multipart），即 Mule 把 multipart parts/attachments 建模为类型化值而非裸字节。
- Mule 运行时流式/可重复流、临时盘缓冲等细节**本次未能抓到可引用页面（文档站访问受限，证据级②/③）**，不展开、不下数字结论。

**Boomi（证据①，连接器资源管理）:**
- Boomi 官方把 connector 的输入/输出明确建模为 **data stream**，并强约束"流资源必须正确释放，否则 N 个并发操作即可吃满运行堆"（Resource management for data streams，页面属 connector 公开发布硬性要求）。
- 即：Boomi 的文档体天然以"流"存在，连接器按流消费/产出；大文件不是先整读进内存再处理的对象。文档大小/分块/磁盘细节未核实到页面。

**对我们 FileRef 的借鉴点：**
- "一等 Binary 类型 + multipart 类型化"提醒：**契约 schema 里给 file/binary 留类型位**是重型平台的一致做法（我们的 A9 契约变更方向正确）。
- "流 + 资源释放纪律"印证：文件流功能的工程重心一半在"谁持有流、谁释放、如何防 OOM"，而非协议层。

### 4.4 AWS / Kong / Google（云网关与对象存储作为"文件引用层"）

云生态的共同结论：**编排/网关不负责"持有"文件字节，文件住在对象存储，编排以 key/URL/预签名引用它**；网关做流式透传 + 大小限额。这从基础设施层面再一次支持"句柄/引用"模式。

**AWS（证据①）：**
- **Lambda（作为代码执行器）**：同步调用请求/响应 **各 6MB**；**streamed response（同步）可达 200MB**；异步 1MB。即"想让函数直接吞吐文件 → 6MB 天花板，超了就 S3 中转或流式响应"。函数 `/tmp` 目录 512MB–10,240MB 可当临时盘（upload 到 S3 后再处理）。
- **API Gateway**：抓到的配额页正文为限流配额（10,000 RPS 等）；"每请求 payload 上限"位于同页后续小节，本次静态抓取未截获（证据级：页面=①，该数值=②/未提取）。
- **S3（对象存储，事实上的"文件引用 + 大文件"层）**：单 PUT ≤5GB；**multipart upload 覆盖 5MB–50TB**，官方定位即"为超大对象优化、可并行分片"；**大对象从盘上传时 SDK(CRT) 自动切"盘→流直传"，避免在内存缓冲**（内存流方案则每部分最多 5GB 缓冲、受内存限制）。
- AWS AppFlow / Application Integration 本次未抓取（证据级③）；按产品定位 AppFlow 面向"记录型数据流"而非字节透传，此条不作结论仅作背景备注。

**Kong（证据①）：**
- 提供 **Request Size Limiting 插件**（默认按 MB，可配 byte/KB/MB），用于给 Gateway Service 加 body 上限（防 DoS）——证明"网关层可流式转发上传体，是否限流由插件策略决定"，而非网关自身吞全量。
- 网关对文件/二进制不做对象模型，纯粹字节透传；不提供脚本加工。

**Google Apigee（证据级②）：** `limits` 页面两次抓取超时；按其公开定位 Apigee 属 API 网关/代理层，对请求/响应按代理缓冲透传，配置了规模限额（含 payload/消息大小），但本次无法引正文，故矩阵该行按 ②/未核实处理。

**对我们 FileRef 的借鉴点：**
- "6MB 同步请求天花板 + 200MB 流式响应 + S3 引用"是"内存 Map 上限 16MB 症结"的行业同款叙事——**所有平台都在某处画了"直接进执行器"的字节红线**，谁都没做"任意大字节直接进运行时内存"。
- S3 的"盘→流直传、内存流才缓冲"与我们"DataBuffer 流式落盘、不整读"同一哲学；预签名/URL 直传是"避免字节穿过编排"的终局手段。

### 4.5 国内厂商参照：企业微信"先上传拿引用（media_id）"

企微不提供我们意义上的"编排"，但它代表国内 PaaS 最典型的文件传递契约，对 FileRef 的"引用 + 有效期"语义是极佳参照（证据①，上传临时素材接口）：

- **契约**：`POST /cgi-bin/media/upload?type=file`，multipart/form-data 上传（字段名 `media`，携带 filename/filelength/content-type）→ 返回 `media_id`；下载走 `GET media/get` 按 media_id 拉取（`media_id` 同一企业应用间共享，**3 天有效**）。
- **上限**：所有文件 >5 字节；image 10MB（JPG/PNG）、voice 2MB（AMR）、video 10MB（MP4）、**普通 file 20MB**。
- **对超限文件的应答在上游而非编排**：提供"**异步上传临时素材**"（大文件异步）与**微盘**的文件上传/下载/**文件分块上传**（均在素材/存储 API 层）。
- 即：国内模式 = "**上传即入库拿引用 → 集成传引用 → 按引用下载**"，引用**自带过期时间**，大文件/分块是**存储服务**能力而非编排能力。

**对我们 FileRef 的借鉴点：** 企微把"3 天 TTL + 空间隔离(企业/应用) + 引用跨步共享"做进了引用本身 → 我们的 FileRef 建议形态中 `expireAt` 字段与此一致；"引用带 TTL"比"依赖用户删文件"更接近国内惯例。

## 5. 关键启示与对标

### 5.1 各家覆盖到 S1–S4 哪一层（对照我们的场景划分）

> 口径：S1 下载→透传（字节不解释返回）；S2 上传→转发；S3 大 JSON/文本透传；S4 加工二进制。"引用直传"即整链只传引用/URL、字节不流经编排。

| 平台 | S1 | S2 | S3 | S4 | 说明 |
|---|:--:|:--:|:--:|:--:|------|
| n8n | ✅ | ✅ | ◑ | ✅（显式 API） | 天然支持 download→binary→上传/返回；大文本走 json 或二进制；加工=代码节点显式取 Buffer |
| Workato | ✅ | ✅ | ◑ | ◑（内建工具） | 下载动作 + streaming；S3=URL 直传或 file content；加工以 File tools/SQL 转换为主 |
| MuleSoft | ◑ | ◑ | ◑ | ✅（DataWeave） | 表达式引擎原生处理 Binary（类型层已核实，端到端流程未核实） |
| Boomi | ✅ | ✅ | ◑ | ◑ | 流式 data stream 模型已核实；细节未核实 |
| AWS(Lambda/S3) | ✅ | ✅ | ✅ | ✅（无沙箱） | 下载/上传都以 S3 引用完成；加工=任意代码但受 6MB/内存/超时/沙箱缺失约束 |
| Kong | ✅（透传） | ✅（透传） | ✅（透传） | ❌ | 纯字节旁路，无加工面 |
| 企微（参照） | ✅（按 media_id 下载） | ✅（上传拿 media_id） | ❌ | ❌ | 只有"引用式上传/下载"，无编排、无加工 |

**读法**：没有任何一家商用/开源平台把 S4（沙箱内自由加工任意字节）当默认能力；S1/S2 靠"下载/上传 + 引用直传"已是标配；S3（大文本/大 JSON）各家走"分块/流式/落盘"，鲜见"一次性内存 Map 展开"。

### 5.2 对 FileRef 句柄式方案：可用 / 可借鉴 / 需规避

| 类别 | 条目 | 出处 | 含义 |
|------|------|------|------|
| **印证（可用）** | 成熟平台普遍"文件与 JSON 分域"（n8n binary 并列于 json；MuleSoft Binary 一等类型；Workato datapill；Boomi data stream） | n8n/MuleSoft/Workato/Boomi ① | FileRef 作为第二数据形态是行业主流，不是自创 |
| **印证（可用）** | 引用/存储都带生命周期：Workato FileStorage 手动清理、企微 media_id 3 天 TTL、n8n 随执行数据修剪 | ① | FileRef 必须带 TTL/回收策略，与评估报告 §5.2 一致 |
| **借鉴** | n8n 代码节点用 `getBinaryDataBuffer()` 显式取字节（Python 不支持、受控） | ① | 给 `ctx.fs.readBytes(fileRef,{maxBytes})` 提供了产品级先例（"沙箱内显式 API 才见字节"） |
| **借鉴** | Workato "file content 才可加工、URL 直传才适合大文件"的两档话术 | ① | 透传 vs 加工的分档可直接用于产品叙事；MVP 先透传、再开受控加工 |
| **借鉴** | Workato 流式动作设计成"长/延迟动作、不超时" | ① | 大文件传输的超时语义要单独设计（我们风险 §7.4 的同款解法） |
| **借鉴** | n8n filesystem↔queue 冲突、database 单文件 512MiB 上限 | ① | 我们的"临时盘 MVP"在多实例下要切换共享对象存储；单文件上限要显式建模而非依赖 JVM |
| **需规避** | AWS Lambda 6MB 同步请求/响应天花板 | ① | 我们不应把"文件能进结果/缓存对象（Redis 全量 JSON）"当成可承载大字节的通道（评估报告症结 6 同向） |
| **需规避** | Node-RED function 节点任意操作 Buffer（无沙箱无配额） | ① | 多租户场景绝不能照搬"代码全权摸字节"；安全边界必须留在平台侧 |
| **需规避** | Workato FileStorage 无自动删除（用户手动清） | ① | 托管存储若不配 TTL/孤儿巡检，会积累存储债（我们 B4 生命周期深化必要） |

### 5.3 "脚本加工 + 安全沙箱"各家怎么平衡

| 模型 | 代表 | 形态 | 安全边界 | 对我们 S4 的含义 |
|------|------|------|---------|-----------------|
| A. 内建节点做文件操作，脚本只碰结构化数据 | Workato（File tools、转换器）、n8n（Convert/Extract/Compress 等节点） | 文件能力封装成节点/工具 | 用户写不了任意字节 IO | S4 若走"产品化工具节点"路线可完全绕开沙箱风险；代价是灵活性低 |
| B. 沙箱内显式 API 才给字节 + 配额 | n8n `getBinaryDataBuffer()` | 代码节点可读 Buffer | 仍受平台执行环境约束、有上限 | 与我们的 `ctx.fs.readBytes` 白名单同构，可行且已有开源先例 |
| C. 无沙箱、代码全权（自托管/可信环境） | Node-RED function、AWS Lambda | 任意代码碰 Buffer/对象 | 无内置沙箱；风险由运行环境隔离承担 | 多租户 SaaS 不适用；可作为单租户/私有化选项对照 |
| D. 表达式引擎类型化处理字节 | MuleSoft DataWeave Binary | 在类型系统内 base64/blob 加工 | 表达式比任意代码面小 | 说明"语言级字节类型"本身是安全面收窄的一种手段 |

**结论**：本次未发现"多租户商用平台把任意字节 + 自由 IO 直接交给用户脚本"的先例；S4 的可行路径收敛到 A（内建工具节点）或 B（沙箱显式白名单 API），与可行性评估 §5.4「受限 fs API 白名单、不放 allowIO」的判断一致。

### 5.4 大文件处理策略共性——印证还是挑战我们"落盘 MVP"方案

**共性（均证据①）：**

1. **没有"大字节直接进编排内存"的成功叙事**。所有大文件路径要么落盘（n8n filesystem、Lambda /tmp、S3 盘→流直传），要么对象存储中转 + 引用（S3/Workato FileStorage），要么分块 streaming（Workato/多线程上传 API）。
2. 落盘/对象存储在规模化部署时是**共享存储**而非本机盘：n8n queue 模式强制 database 模式；Boomi 强调流资源释放纪律。
3. 平台普遍画"直接进执行器的字节红线"（Lambda 6MB、API GW ~10MB、n8n database 512MiB、企微 20MB media），把更大交给存储层。

**对 MVP（落临时盘 + DataBuffer 流式读写）的判读：**
- **印证**：落盘方向对；"盘→流直传/不整读内存"与 S3/CRT、n8n filesystem 同一哲学；我们的 16MB 红线症结就是行业里被画红线的那条线，必须用流式 codec 突破而非调大内存。
- **挑战/需预留**：MVP 用本机临时盘即可，但要像 n8n（filesystem↔queue 冲突）那样**在架构上预留共享对象存储后端**（评估报告 §5.2 FileStorageStrategy 已含 local/MinIO/OSS 抽象）；单文件上限、TTL/孤儿清理要与"执行记录保留期"联动（n8n 把 binary 清理挂 execution pruning，Boomi/Workato 同向）。

### 5.5 Non-Goal（断点续传/分片/秒传/转码）行业普遍性验证

| Non-Goal | 行业位置 | 证据 | 判读 |
|---------|---------|------|------|
| 断点续传 / HTTP Range | 对象存储/内容分发层普遍能力（S3 Range、网关透传天然兼容） | S3 页（隐含 range 语义）、网关流式 | **普遍不属于编排引擎**；因"透传"与 Range 天然兼容，可低成本二期做，不建议永久排除 |
| 分片上传 | 存储服务/大文件 API 层（S3 multipart 5MB–50TB、企微微盘文件分块上传、Workato OneDrive upload large file via session） | AWS① / 企微① / Workato① | **存储层标配，编排层普遍不实现** → 我们列为 Non-Goal 成立 |
| 秒传/去重 | 属存储/客户端能力，未见于各编排引擎文档 | 未发现编排侧实现 | 成立 |
| 文件转码 | 各平台以独立产品/节点提供（n8n Edit Image、Workato compress/transform、企微素材 type 限制） | n8n/Workato ① | 平台以"增值节点/产品"提供而非核心，作为 Non-Goal + 扩展点是合理的 |

**结论：Non-Goal 合理。** 行业共识是"编排引擎做字节的流式透传与受控加工，把断点/分片/秒传/转码留给对象存储与独立增值能力"。但要注意区分"Non-Goal（不实现）"与"兼容（不破坏）"：我们的出口旁路写回若保持 HTTP 流式语义，上游对象的 Range 请求在二期可低成本支持。

| 我方决策 | 行业支持度 | 一句话理由 |

| 路线 B：FileRef 句柄式（字节不进 JSON 图） | **高** | n8n/Workato/MuleSoft/Boomi/AWS-S3 全部是"文件独立于 JSON/以引用或流存在" |
| 透传 MVP（S1–S3）先于 S4 | **高** | Workato 明确"URL 直传（不解释）才是大文件通道、加工(file content)才需要内容进编排" |
| S4 = 受限 fs API 白名单而非放开 allowIO | **高** | 无多租户平台放任自由 IO 的先例；n8n 显式 buffer API = 现成同构先例 |
| 出口旁路流式写回（不经 Jackson/base64） | **高** | Lambda streamed response / 网关透传 / S3 流直传，行业无"文件 base64 回 JSON"的正向叙事 |
| Non-Goal：断点/分片/秒传/转码 | **高** | 均属存储层/增值层能力；编排引擎普遍不做 |
| 存储层：临时盘 MVP → 对象存储（local/MinIO/OSS） | **中高** | 方向正确；但需预留"共享存储 + 单文件上限 + TTL 联动清理"，避免 n8n filesystem/queue 冲突与 Workato"无自动删除"式的存储债 |

### 6.2 可落到我们实施的具体要点（按证据①）

1. **FileRef 元数据模型补一个"生命周期来源"概念**：n8n 把清理挂在"执行数据修剪"，企微把有效期挂在引用本身（media_id 3 天），Workato 把留存挂在用户显式删。我们的 `cp_file_ref_t` 建议对齐"执行记录保留期（30 天）联动 + 可选 TTL"双轨（A7/A8 工作项已含日志只记元数据，可再加一条"文件删除跟随执行清理"）。
2. **流式动作的"不超时"语义要单独设计**（Workato 把 streaming 动作做成 long/deferred 不超时）：文件流若复用 JSON 流的 timeoutMs 会在百 MB 下载上误杀；建议"总时长 + 字节进度双控"（呼应可行性评估风险 §7.4）。
3. **脚本取字节走"显式 API + 单次/总量配额"**，形态可直接参考 n8n `getBinaryDataBuffer(itemIndex, propertyName)` 与 Workato 公式 base64 编解码：做成 `ctx.fs.readBytes(fileRef,{maxBytes})` 白名单（S4 档）。
4. **契约与 UI 上给 file/binary 类型位**（MuleSoft 一等 Binary + Multipart 类型）：A9/A10 方向正确；可把"file 类型字段"同时用于"输出透传开关"与"脚本取字节入口"两种语义。
5. **单文件上限显式建模**（n8n database 512MiB、企微 file 20MB、S3 5GB 单 PUT 的参照系）：建议 MVP 明确"流式落盘的单文件上限（如 200MB，对齐可行性评估 A 档）"与"直接进内存的表达式/JSON 上限"分开设置——避免把 16MB 的"全量缓冲红线"误当成"文件大小红线"。

### 6.3 一句话总结

> 竞品不回答"要不要支持文件"，只回答"字节放在哪、以什么引用传递、加工时开多大的门"。我们的 FileRef + 透传 MVP + 受限 fs 白名单 + 明确 Non-Goal，与行业（尤其 n8n/Workato/S3 三个样本）的主流向完全一致；差异点仅在于把"存储生命周期治理"与"流式传输的超时/上限语义"在设计之初就做进地基，而不是等大文件压测再补。
