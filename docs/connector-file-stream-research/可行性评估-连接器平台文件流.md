## 1. 执行摘要

**一句话结论：现有连接器平台以「JSON Map 全量内存」为唯一数据形态，不具备任何字节流/流式/大文件能力；文件流无法作为现有 JSON 编排的自然副产品获得，需要一次架构级扩展；但该扩展有清晰的「透传 MVP → 通用文件流」两段路径，改造可收敛、可验证，建议推进。**

| 判断项 | 结论 |
|--------|------|
| 现有能力能否支撑文件流？ | ❌ **不能**。11 项证据逐条核实：入口 JSON-only、连接器/脚本 HTTP 全字符串、16MB 内存上限、输出仅 JSON 可序列化对象、执行日志快照轻量化设计、脚本沙箱 `allowIO(false)`。文件流不是缺某个节点能力，而是整条数据平面（触发 → 连接器 → 脚本 → 出口 → 日志）都建立在「JSON 对象图」之上。 |
| 是否建议做？ | ✅ **建议做**，但按「透传 MVP」先行。真实业务诉求（文件上传/下载）无法绕开；现有通用文件表 `openplatform_common_file_t`（V5）提供了文件元数据存储参考，说明平台已有文件领域雏形。 |
| 首选改造路线 | **FileRef 文件引用（句柄式）**，而非「文件内联进 JSON」。理由见 §5。 |
| MVP 锚点链路 | 下行下载透传链路 + 上行上传透传链路（均不经过脚本加工）。见 §8。 |
| 改造总量级 | 透传 MVP 约 **35–50 人日**（含契约/前端编排）；完整通用文件流（含脚本受限 IO）约 **75–105 人日**。见 §6。 |
| 明确 Non-Goal | 断点续传、分片上传、秒传、文件转码、服务端流式渲染等一律不做（见 §7.5）。 |

## 2. 业务定位与场景分类

### 2.1 场景语义矩阵

将「连接器平台支持文件流」拆成四种可独立评估的场景语义。划分的轴是 **数据形态**（结构化 JSON vs 原始字节 vs 大文本）与 **是否加工**（透传 vs 转换）。

| 场景 ID | 场景名称 | 数据形态 | 典型链路 | 平台角色 |
|---------|---------|---------|---------|---------|
| **S1** | 下载 → 透传 | 下游响应体为文件字节（任意 content-type，如 PDF/ZIP/图片） | HTTP 触发 → 连接器 GET 下载 → Exit 返回字节给调用方 | 反向代理 / 字节搬运 |
| **S2** | 上传 → 转发 | 调用方上传文件字节（multipart 或 raw body） | HTTP 触发(含文件) → 连接器 POST 上传至下游 → Exit 返回确认 | 上传代理 / 字节搬运 |
| **S3** | 大 JSON / 大文本透传 | body 是超 16MB 的 JSON 或纯文本（仍是字符数据，但突破内存上限） | HTTP 触发 → 连接器 → Exit | 大报文透传 |
| **S4** | 脚本加工二进制 | 字节进入脚本节点，JS 读取/转换/生成后继续流转或输出 | HTTP 触发 → 连接器下载 → 脚本处理 → Exit / 上传 | 加工执行器 |

### 2.2 透传（S1/S2/S3）vs 加工（S4）的本质差异

| 维度 | 透传（S1/S2/S3） | 加工（S4） |
|------|-----------------|-----------|
| 数据是否必须进内存对象图 | 否——可整链**旁路流式**（字节流经节点时不展开成 Map，仅携带句柄/引用） | 是——脚本需要**随机访问**字节内容 |
| 与沙箱安全的关系 | 无直接冲突（字节不在 JS 堆内） | **直接冲突**——脚本沙箱 `allowIO(false)` 禁止文件 IO；要让 JS「摸到」字节必须新增受控通道 |
| 复杂度量级 | **低**（链路上换数据载体 + 存储） | **高**（类型系统 + 沙箱白名单 API + 内存上限 + 资源回收） |
| 是否阻塞 MVP | 否（MVP 全部是透传场景） | 是（MVP 应明确排除 S4） |

> ⚠️ **关键设计含义**：S1/S2/S3 虽然都叫"文件流"，但实现上共享「存储层 + FileRef 句柄 + 流式读写」这套地基；S4 在此地基之上叠加「脚本可读字节」能力。因此**透传 MVP 与通用文件流是同一架构扩展的两档交付，不是两个方案**。

### 2.3 与连接器节点既有"非 JSON 响应"兜底的关系

现状：连接器节点对非 JSON 响应只是塞进 `body.rawResponse` 字符串字段（证据 E3），这在语义上**不是文件支持**——它是"把任意响应文本当字符串存下来"，上限受 16MB 内存约束、且丢失二进制保真（字符串化字节）。

## 4. 核心架构症结

把上面的证据收敛为 **6 个症结**，按严重度排序：

### 症结 1（🔴 最高）：数据形态锁死为「JSON Map 全量内存」
**证据**: E1/E2/E4/E5/E6 + E10 数据契约。
**说明**: 这是**元症结**。触发输入、节点上下文、节点输出、执行结果、日志、DB 存储全部以 `Map<String,Object>` 为唯一载体。任何 >内存、非 JSON、需要流式的东西在这套模型里都没有"座位"。文件流要落地，**必须先引入第二个数据形态（字节/文件句柄），并让它在整条链路上有合法通道**——这是结构性变更，不是加个字段。

### 症结 2（🔴 高）：16MB 硬内存上限贯穿出站/入站 HTTP
**证据**: E8（RuntimeConfig WebClient 16MB）。
**说明**: 连接器节点的每一次出站与入站响应都受此限制。即便文件只有 17MB，下载→透传也会在第一步失败。**注意**：这不是"调大 maxInMemorySize 就行"——调大只是把"更早失败"变成"内存崩溃"，全量缓冲本质不变。必须改成流式 codec（DataBuffer 流）+ 磁盘/对象存储落盘，才能根本解决。

### 症结 3（🟠 中高）：出口/入口是"JSON 专属"，无原始字节通道
**证据**: E1（入口 consumes=JSON）、E9（出口 body 交 Spring 序列化 → byte[] 变 Base64）。
**说明**: 文件下载的本质是"把下游字节流原样写回响应流"，文件上传的本质是"把请求字节流原样转发"。当前入口/出口都被 JSON 信封思想占据；`TransparentFlowResponse.body` 塞 byte[] 会掉进 **Base64 陷阱**（膨胀 33%、仍全量内存、丧失 content-type 语义）。出口需要一条**旁路流式写回通道**（绕过 Jackson 序列化，直接写 DataBuffer），入口需要 multipart/octet-stream 解码分支。

### 症结 4（🟠 中）：执行日志快照是轻量 JSON 设计，容不下文件体
**证据**: E10（execution_step_t 每次全量写 input/output JSON；plan-db 意图 TEXT≤64KB 轻量快照，实际 DDL MEDIUMTEXT）。
**说明**: 执行步骤日志对每个节点**全量**快照 input/output。文件体一旦进入节点 input/output Map：
- 快照字段被撑爆（数十 MB 文件体 × 每次执行 × 每节点）；
- 日志脱敏 `LogSanitizer`/序列化本身就要把整个 Map 转 JSON（ExecutionStepService toJson）——内存二次放大；
- DB 膨胀拖垮 execution 查询与 FIFO 清理。
**必须的配套**：日志链路对"文件句柄"只记元数据（refId/size/contentType/文件名），**绝不落文件体**；对大文本/大 JSON 做截断策略。

### 症结 5（🟠 中）：脚本沙箱无 IO 与"脚本加工文件"冲突，属架构级安全取舍
**证据**: E11（GraalJsContextFactory 五层防御 allowIO(false)）。
**说明**: 这不是"忘了加权限"，而是**刻意设计的纵深防御**（E11 注释明确）。V3 把脚本定位为"复杂逻辑兜底"，安全边界是硬约束。文件加工需求若直接放开 `allowIO(true)`，等于摧毁整个沙箱模型（任意文件读写 = RCE 级风险）。**唯一可走的路是"受限 fs API 白名单"**——仿照已有先例（ScriptHttpClient 绕沙箱经白名单通道提供 HTTP 能力，见 §5.4），新增 `ctx.fs` 类通道，只允许操作平台分配的 FileRef 对应存储对象，禁止任意路径。此症结决定 S4 的工期与安全设计深度。

### 症结 6（🟡 中低）：契约/前端/缓存未预留文件语义
**证据**: E10（JSON Schema 无 file 类型）、E2（缓存按 Map 表达式构建、结果整体 JSON 化）。
**说明**: inputContract/outputContract 无文件类型；前端编排器（wecodesite FlowEditorV2 等）无文件字段映射 UI；结果缓存对文件场景需要"只缓存元数据/禁缓存"策略。这些是"跟随性"工作，但因涉及**契约 schema 版本变更**（编排快照存 DB，旧流版本兼容），需要在改造中单列工作项，不可遗漏。

## 5. 改造方案（仅评估）

### 5.1 两条路线：文件内联 vs 文件引用（FileRef）

#### 路线 A：文件内联（把字节当 Base64 字符串/大文本塞进 JSON Map）

| 步骤 | 做法 |
|------|------|
| 入口 | 增加 multipart 分支，读 `MultipartFile.getBytes()` 或 `bodyToMono(byte[].class)` |
| 传递 | 将 byte[] 转 Base64 String（或直接塞 `String` 大文本）放入 triggerData.body |
| 出口 | 从 Map 取回 Base64 解码写回 |

**评估**：
- ❌ 字节 → Base64 → String 膨胀 33%，全程多份内存拷贝（请求缓冲一份、String 一份、解码一份）。
- ❌ 16MB 上限问题**没有解决**——String 反而比字节更占内存。
- ❌ 节点间每次流转都复制整份大对象；DAG 调度/上下文快照/日志全被拖垮。
- ✅ 唯一优点是"不引入新数据形态"——但这是虚假优点，因为该形态根本容不下文件。
- **结论：只在"极小文件 + 极简链路"（如 <1MB 图标上传）的退化场景可用，不作为文件流架构方案。** 实际上平台已有独立文件表承载此类（V5 common_file，biz_type=1/2），应走文件模块而非连接器链路。

#### 路线 B：文件引用 FileRef（句柄式，推荐）

**核心思想**：文件**内容永不进 JSON 对象图**。链路中流转的是一个轻量句柄 `FileRef`，真正字节落在平台文件存储，需要读写时按句柄流式存取。

**FileRef 建议形态**（JSON 可序列化，可进 Map/日志/契约）：

```json
{
  "fileRefId": "6500123456789012345",     // 雪花/分布式 ID，指向文件存储
  "fileName": "report.pdf",               // 原始文件名（透传用）
  "contentType": "application/pdf",       // MIME（透传/断点用）
  "size": 2048576,                        // 字节数（阈值判断/日志用）
  "storage": "local|oss|minio",           // 存储后端标识
  "expireAt": null                        // 可选 TTL（安全回收）
}
```

**链路行为变化**：

| 环节 | 现状 | 改造后 |
|------|------|--------|
| HTTP 入口 | 只认 JSON Map | content-type 为 multipart/octet-stream 时，解码为 DataBuffer 流 → 写文件存储 → `body.file = FileRef`（其余字段照旧 JSON） |
| 连接器出站 | `.bodyValue(Map)` | body 映射到 FileRef 时改为流式上传（WebClient body 为 `BodyInserters.fromResource/DataBuffer`） |
| 连接器入站 | `bodyToMono(String)` + readValue | 按响应 content-type 分流：JSON → 照旧解析；文件/二进制或超阈值 → 流式落盘 → `body.file = FileRef`（含文件名/content-type 来自响应头） |
| 脚本节点 | ctx 内上游 output 是 Map | 上游输出中的 FileRef 以 JS 对象形态进入 ctx；配合 ctx.fs 白名单 API 读取字节（S4） |
| Exit 出口 | output.body → 交 Spring 序列化 | output.body 含 FileRef 且出口声明透传 → **旁路流式写回**（绕过 Jackson，直接 DataBuffer → ResponseEntity），content-type/Content-Disposition 取自 FileRef |
| 执行日志 | 全量 input/output JSON | FileRef 只记元数据（天然 JSON 化，轻量）；大文本截断策略 |
| 缓存 | 整体 JSON 化 | 命中含 FileRef 的结果时只缓存/返回元数据 + 存储引用（或标记该流不可缓存） |

**优点**：
- 解决症结 1（引入第二数据形态，且可 JSON 化进现有 Map 座位）、症结 2（内容不占内存）、症结 3（出口可流式旁路）、症结 4（日志只记元数据）。
- FileRef 本身是普通 JSON 对象 → **表达式、节点输出、契约 schema、现有 JSON 编排全部兼容**（只需扩展 schema 加 file 类型），改造是"加法"而非"推翻"。
- 天然支持 S1/S2/S3：透传时整链只搬运 FileRef + 存储引用，字节真正读写只发生在入口落盘与出口写回两处。

**缺点/代价**：
- 需要**文件存储层**（本地盘/MinIO/OSS 抽象 + 生命周期/回收/TTL）；
- 文件内容"落盘"引入 I/O 与临时文件管理成本；
- 出口旁路写回需要改响应构建路径（不再是统一 Object 序列化）。

**结论：推荐路线 B**。理由：①它是唯一能同时化解症结 1–4 的路线；②FileRef 以 JSON 句柄形态嵌入现有 Map 模型，迁移成本与旧流兼容性最优；③平台已有 V5 `openplatform_common_file_t` + `FileStorageStrategy` 抽象（Standard/Dev 双策略）可作为存储层参考基线，不是从零造轮子。

### 5.2 存储层建议

- **表模型**：参考 V5 `openplatform_common_file_t`（batch_id/file_name/file_path/biz_type/file_size/content_type/create_time），新增/复用文件元数据表；为区分业务域建议新增 `cp_file_ref_t`（或扩展 common_file 增加 `biz_type` 值域 + 关联 execution/flow 字段）。
- **存储后端**：`FileStorageStrategy` 接口（已有 Standard/Dev 实现先例）抽象 local/MinIO/OSS；连接器运行时文件默认 TTL 回收（如 24h 未引用即清），执行记录保留期对齐现有 30 天清理策略（plan-db §6.1）。
- **流式 codec**：WebClient 出站/入站启用 `DataBuffer` 流式处理（替代 `bodyToMono(String)` + 16MB maxInMemorySize），或对"已知文件响应"使用 `exchangeToMono` + 手动落盘。

### 5.3 出口旁路流式写回

`TransparentFlowResponse` 当前承载 Object body + headers。改造方向（两条可选，评估层面二选一，实现时再 ADR）：
- **方案 1（推荐）**：出口输出含 FileRef 时，构建响应不走 `Object body` 序列化，而由 Controller 层检测到 FileRef 后改用 `ResponseEntity<Resource>` / `ServerResponse` 流式写回（content-type/length 来自 FileRef）。
- 方案 2：新增专用下载端点（如 `/flows/{id}/files/{fileRefId}`），文件下载经二次 URL 跳转。**不推荐为主方案**：改变调用方契约、多一次跳转、增加 URL 泄漏面；仅作为"异步/断点"场景的扩展。

### 5.4 脚本沙箱：受限 fs API 白名单（不放开 allowIO）

**结论先行**：S4 需要的是「脚本可安全访问平台文件」，**绝不是**放开 `allowIO`。

设计方向（参考 ScriptHttpClient 既有绕沙箱模式——白名单 Java 对象经 `HostAccess.Export` 注入沙箱）：

```js
// ctx.fs 注入（新增白名单对象，允许方法级导出）
ctx.fs.readBytes(fileRef, { maxBytes: 8*1024*1024 }); // 返回 Uint8Array（受大小上限保护）
ctx.fs.writeBytes(fileName, data, { contentType });   // 返回新 FileRef（落平台存储）
ctx.fs.stat(fileRef);                                  // 元数据
// 明确禁止：任意路径、绝对/相对路径字符串、目录列举、进程/网络原生访问
```

**白名单约束**（必须同时满足）：
1. **只能操作 FileRef 句柄对应对象**，不接受用户任意路径字符串；
2. 单次读上限（如 8MB）与单脚本总配额，防内存/存储耗尽（与现有 STATEMENT_LIMIT 呼应）；
3. 写入内容受 contentType 白名单 + 病毒扫描预留位；
4. 文件 TTL/引用回收：脚本产出的临时 FileRef 若不流转至出口/后续节点即清理。

> ⚠️ 若业务只要求透传（S1–S3），**沙箱完全不动**；沙箱扩展只在 S4 档投入。

## 7. 风险与关键权衡

### 7.1 内存峰值与背压
- 透传场景内存应保持 O(1)（流式落盘/写回），但**表达式求值、日志快照、脚本 ctx 组装**三处会尝试把 FileRef 内容展开——必须设全局与单流字节阈值，超限即错误提示而非 OOM。
- WebFlux 反应式链路本身有天然背压，但现有 DagScheduler 若对节点输出做整体内存持有，需确认上下文生命周期内 FileRef 只存句柄不存内容。

### 7.2 脚本加工 vs 沙箱安全（最敏感权衡）
- **绝不可** `allowIO(true)`。这等于把任意文件读写交给多租户用户脚本 = 高危漏洞。
- 白名单 `ctx.fs` 仍是"在沙箱墙上开一扇小门"，风险取决于门的口径：只接受 FileRef、强配额、内容类型白名单、全审计。需要一次正式安全评审（建议 ADR + review 阶段专项）。
- 若安全团队无法接受任何脚本文件 IO，则 S4 应降级为"不支持"并在产品层明示（文件流仅透传）。

### 7.3 缓存 / 限流 / 审计在文件场景的行为
- **缓存**：文件流结果不应进现有 Redis 全量缓存（Base64 膨胀 + 存储浪费）。语义应改为：文件流只支持"元数据级缓存"或关闭。
- **限流**：现有按 QPS/maxConcurrency 的入站限流（FlowInvokeService validateRateLimitConfig）对文件流不充分——大文件需字节/带宽级限制，避免单请求拖垮吞吐。
- **审计**：执行记录/步骤日志只落文件元数据；文件内容的合规（敏感内容扫描）是平台治理问题，超出本次范围但需预留扩展点（contentType 白名单 + 扫描钩子）。

### 7.4 下游/目标地址安全
文件流放大出站数据量，需复核 URL 白名单（连接器目标地址校验沿用既有能力）、出站大小配额、超时在慢文件传输下的语义（现有 timeoutMs 对 100MB 下载可能不够，需按字节进度/总时长双控）。

### 7.5 明确 Non-Goal（不纳入评估范围）
- 断点续传 / Range 请求支持（下载断点）——HTTP Range 语义与"透传"天然兼容，但属增量增强，建议二期；
- 分片上传 / 秒传 / 大文件并发直传通道；
- 文件转码 / 预览 / 病毒扫描（预留扩展点，不实现）；
- 将文件流能力复制到数据开放平台等其他域。

### 7.6 兼容性风险
- **契约 schema 变更**会触及已部署流版本快照（DB 中编排 JSON 无 file 类型 = 向后兼容即可，旧流不受影响，但 schema 校验器需做"未知类型放行/报错"决策）。
- **WebClient codec 流式化**回归面最大——所有既有 JSON 连接器调用必须全绿。

## 8. 结论与建议路径

### 8.1 明确回答

> **Q: 现有能力能否支持文件流？**
> **A: 不能。** 不是"缺一两个功能点"，而是数据平面整体建立在 JSON Map 全量内存形态上，与"文件字节流"在入口、连接器、脚本、出口、日志五层全部冲突（§3 证据 E1–E11、§4 症结 1–6）。任何"看起来能支持"的捷径（Base64 内联、调大 16MB、rawResponse 塞字符串）都是把问题从"明确失败"变成"隐蔽崩溃"，不可取。

> **Q: 是否建议做？**
> **A: 建议做，但分两档。** 业务有真实诉求；改造有清晰收敛路径。首档**透传 MVP（S1 下载透传 + S2 上传转发 + S3 大文本）约 35–50 人日**，不触碰脚本沙箱，风险可控；S4 脚本加工因涉及沙箱安全白名单，建议第二档独立评审后推进。

### 8.2 建议首个 MVP 锚定的链路

**推荐 MVP 范围**：S2 上传→转发（小）→ S1 下载→透传（小）→ S3 大 JSON/文本透传。若只取一条验证链路，**优先锚定 S1「下载 → 透传」**：

```
HTTP 触发 → 连接器节点 GET 下载文件(pdf/zip/任意二进制)
         → 响应 content-type 非 JSON → 流式落盘 → body.file = FileRef
         → Exit 节点透传 → ResponseEntity<Resource> 流式写回
         → 调用方拿到原始字节（md5 与源文件一致）
```

**理由**：
1. S1 覆盖了最深的症结（出口原始字节通道 E9 + 入站字符串化 E3 + 16MB E8），是**技术风险最高、验证价值最大**的一段；
2. 文件"下载下来能原样交给调用方"是文件流的最基本承诺，先证明它，其余场景都是同地基复用；
3. S1 不需要脚本、不需要入口 multipart（S2 才需要），MVP 依赖面最小；
4. 验证标准清晰：**字节级一致（md5）+ 超过 16MB + 任意 content-type** 三项通过即为 MVP 达标。

### 8.3 立项路径建议

本报告是 **前置可行性评估**，不属于任何 specs-tree feature 生命周期产物。若决定推进：
1. 通过 `@sddu 开始 连接器平台文件流`（或 discovery 起）正式立项，在 specs-tree-root 下建 `specs-tree-connector-platform-file-stream/`，本报告作为 discovery 输入迁入；
2. discovery/spec 阶段重点决策：A 档 vs A+B 档范围、FileRef 的存储后端选型、沙箱 fs 白名单口径；
3. plan 阶段产出：FileRef 类型与契约 schema、存储层 DDL、流式 codec 改造方案、旁路写回设计，并以 ADR 固化「路线 B + 沙箱白名单」两个关键决策。
